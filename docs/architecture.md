# 架构与请求流

DevSpace 将“对话中的协调”与“本机执行”分开。客户端负责提出和审查操作，服务端
负责协议、工作区身份、权限边界、执行生命周期及结果交付。

本文只描述本仓库的通用结构，不描述任何实际接入项目或私人部署。

## 分层结构

### 协议入口

`src/server.ts` 组合 HTTP、OAuth、MCP 会话和工具注册。认证发现端点用于建立
连接，受保护的 MCP 操作需要有效令牌。MCP 会话是传输上下文，不是项目目录，
也不等于长期代理任务。

`src/tool-surfaces/` 按工具界面组织参数和结果。项目操作与代理桥接在现有
服务内注册，而不是另外开启一个公开的提供方控制端口。

### 工作区层

`WorkspaceRegistry` 将已授权目录表示为工作区，区分实际 checkout 与隔离
worktree。文件、指令和审查操作复用工作区身份。

逻辑路径校验与物理路径校验共同处理目录边界；根目录锚点用于发现恢复前后
目标变化。工作树是协作隔离，不是操作系统安全沙箱。

### 直接执行层

- 项目访问负责清单、搜索、读取、分页与内容哈希。
- 补丁模块负责解析、预检、内容版本校验和文件替换。
- 进程会话模块负责命令执行、输出限制、轮询和终止。
- 审查模块保存 Git 支持的检查点，返回可重新查看的差异。

这些操作不需要启动代理推理。只有明确的代理请求进入委派路径。

### 代理执行层

桥接通过本地客户端连接按需启动的守护进程。守护进程中的任务管理器负责
逻辑任务与权限，运行池管理提供方进程，适配器转换不同提供方的协议。

传输使用本机 IPC。逻辑任务可以持久化，运行进程则可以按空闲策略或失败条件
释放；两者不能混成同一套身份。

### 状态与观测层

SQLite 保存工作区、授权及任务的必要状态。请求回执、根目录锚点和执行证据
服务于重试、恢复与结果核对。日志和工具结果提供观测信息，但不是另一套权威状态。

## 直接文件操作流程

1. 客户端取得已授权的 `workspaceId` 并读取相关项目说明。
2. 根据范围逐页发现、搜索或读取，检查游标、覆盖状态和排除项。
3. 读取目标文件的当前 SHA-256，生成明确的补丁。
4. 使用 `dryRun` 及完整的 `expectedHashes` 检查准备修改的版本。
5. 执行同一补丁，回读内容，运行相关验证并检查差异。

文件读取会检查类型、编码、大小和读取期间的变化。清单快照不是所有文件内容的
原子快照；必须分别处理目录变化和内容变化。

## 代理任务流程

1. 客户端明确给出任务、工作区、请求键及写入模式。
2. 配置了模型策略时，先预检实际执行入口，并在每轮显式传入模型。
3. 桥接核对目录及当前任务，记录交付回执，再联系守护进程。
4. 管理器校验档案、提供方和权限，创建或续接逻辑任务。
5. 提供方执行器建立会话，执行当前轮次并返回结果。
6. 受保护路径校验对应轮次的运行证据，成功后持久化结果。
7. 客户端取得完成或失败状态，向用户报告证据与实际文件影响。

在网络重试中，同一请求复用同一请求键及输入。交付不确定时先核对记录，不能
把新的请求键当成消除错误的方法。目录串行约束目前属于单桥接实例，不是分布式锁。

## 标识与状态

- `workspaceId`：本机项目操作的工作区身份。
- `agentId`：DevSpace 的逻辑代理任务身份。
- `providerSessionId`：提供方的持久会话身份，不是桌面窗口标识。
- `sessionId`：命令执行的进程会话标识，不等于代理任务。
- `requestKey`：一项任务提交或续接的重试身份，不是认证凭据。
- `reviewRef`：可重新读取的差异审查检查点。

代理存储内部使用 `starting`、`running`、`idle`、`error`、`stopped`。
展示层将它们转换为 `running`、`completed`、`failed`、`stopped`；一轮完成后
仍可在显式请求下续接，不能把 `completed` 理解为永久关闭所有上下文。

桥接交付回执中的 `pending`、`accepted`、`uncertain` 描述的是交付状态，
不是模型工作的完成状态。

## 权限与数据流

授权分为不同边界：OAuth 决定客户端是否可以接入，目录规则约束文件工具，
档案和写入模式约束代理请求，具体执行程序及操作系统账户决定实际运行权限。

目录允许列表不能约束任意 Shell 行为。模型策略不等于操作系统沙箱，受保护
执行的证据核验也不会自动撤销已经发生的文件改动。

工具返回的文本、输出和任务结果会传给客户端及其宿主。公开源码、私有运行状态
与模型所接收的上下文是不同数据集合，必须分别管理。

## 失败与恢复原则

- 不把健康接口成功当作业务操作成功。
- 不把提交回执当作任务完成。
- 不把缺失结果当作安全重试的证明。
- 不在失败后自动更换模型或扩大权限。
- 不把模拟提供方测试当作真实模型执行证据。
- 不在有写入者运行时覆盖数据库或恢复不匹配的状态。

现有实现仍有边界：分页可能重复扫描，文本和运行记录有大小限制，部分错误
仍由文本表示，多实例互斥与状态保留策略也需要继续完善。文档不把这些边界
包装成已完成的功能。
